> **上游依赖**：`03_ArtAssetSpec_Procedural.md`（资产面数）、`02_LevelDesign_Hakoniwa.md`（分区与实例密度）、`SceneLayout_SakuraTeien.json`（实例统计）

> **数据来源标注**：本文中 Quest 3 硬件参数、Godot/UE 版本与工具链版本来自公开资料调研（见 §7 来源）；场景面数/DrawCall 来自本项目 `tools/validate_assets.py` 实测。二者分开标注，不混淆。

## 设计思路

VR 的性能预算和普通游戏不是一个量级的问题。普通游戏掉帧是「卡顿」，VR 掉帧是「晕眩」——前庭和视觉信号不一致会直接让玩家反胃。Meta 对 Quest 应用的最低要求是 **72fps**，推荐 **90fps**，这意味着每帧只有约 11ms（90fps）或 13.9ms（72fps）的完整预算，且要**双眼各渲染一次**。这是本项目所有性能决策的出发点：宁可画面素一点，也不能掉帧。

第二个现实是 Quest 3 的渲染管线。它是移动芯片（骁龙 XR2 Gen 2），走的是 Vulkan Mobile/Compatibility 路径，**不能用桌面级的 Forward+ / 延迟渲染 / 实时全局光照 / 屏幕空间反射**。这决定了本项目的渲染方案必须是「烘焙光照 + 单图集材质 + 顶点色 + 极简后期」——这套方案恰好也是 `03` 选定的美术风格，性能与风格是自洽的，不是互相妥协。

第三，本文档给的是**预算（budget）**，即上限，不是实测值。α 阶段无法在真机测（引擎未装、网络不通），所以这里的策略是：把每个能数出来的东西（面数、DrawCall、纹理、粒子）都定一个保守上限，让真机实测时「大概率达标」，即使不达标也知道该从哪砍。所有可离线核算的指标（单资产面数、场景总面数、实例数）已由 `validate_assets.py` 实测锁定；不可离线核算的（真机帧率、内存峰值）标注为「⚠️ 待真机」。

## 一、Quest 3 硬件与目标（公开资料）

| 项 | 参数 | 来源 |
|----|------|------|
| 芯片 | Snapdragon XR2 Gen 2 | Meta 官方规格 |
| 目标帧率 | **90fps**（推荐）/ 72fps（最低） | Meta Quest 应用要求 |
| 每帧预算 | ~11.1ms（90fps），双眼各一次 draw | 换算 |
| 渲染 API | Vulkan（Mobile / Compatibility 路径） | Godot/UE 移动端 |
| 禁用特性 | Forward+、延迟渲染、实时 GI/SDFGI、SSR、体积雾 | 移动端管线限制 |
| 推荐 DrawCall | <150/帧（场景）；VR 建议更低 | 社区经验值 |
| 纹理内存 | 建议 <256MB（含所有 mip） | 移动 XR 经验值 |
| 应用包体 | α 原型建议 <150MB | 本项目目标 |

⚠️ 上述「DrawCall <150」「纹理 <256MB」为移动端 XR 社区经验值，非 Meta 硬性指标；真机需实测校准。

## 二、几何预算（实测）

### 2.1 单资产面数（来自 `validate_assets.py`）

全部 43 个资产均在 `03` §2 预算内，实测合计 **13,400 三角面**（单资产去重合计，非场景实例化总量）。最大单项：

| 资产 | 实测面数 | 预算 |
|------|----------|------|
| `asset_karesansui_frame`（枯山水） | 1,608 | 2,200 |
| `asset_sakura_tree_large`（大樱花树） | 1,448 | 3,200 |
| `asset_kyobashi`（太鼓桥） | 980 | 1,400 |
| `asset_sakura_solo`（独樱） | 848 | 2,000 |
| `asset_sakura_tree_mid`（中樱花树） | 825 | 1,800 |
| `asset_enemy_hikabusho`（绯甲武者） | 636 | 2,600 |
| `asset_tea_stall`（茶摊） | 644 | 1,600 |

角色面数偏低（NPC 508、樱鬼 554、武者 636），因低模 + 单图集策略，符合预期。

### 2.2 场景实例化总面数（估算）

场景共 **159 个实例**（`SceneLayout` 实测）。按实例化后估算可见面数：

| 分区 | 实例数 | 主要资产 | 估算面数 |
|------|--------|----------|----------|
| 鸟居参道 | 31 | 鸟居 280 + 灯笼 208×8 + 竹 364×10 + 樱花 825×2 | ~7,000 |
| 茶摊 | 8 | 茶摊 644 + 灌木/樱花 | ~1,600 |
| 镜池·太鼓桥 | 24 | 桥 980 + 樱花 1448×4 + 石组 | ~11,000 |
| 樱亭 | 12 | 亭 428 + 大樱花 1448×5 | ~9,000 |
| 枯山水 | 12 | 枯山水 1608 + 黑松 415×3 | ~3,500 |
| 石灯笼小径 | 29 | 灯笼 208×11 + 竹 364×n + 樱花 | ~8,000 |
| 樱花林 | 25 | 大樱花 1448×10 + 独樱 848 | ~16,000 |
| 奥之森 | 18 | 黑松 415×7 + 武者 636 + 石组 | ~5,000 |
| 全局（天空/雾） | 9 | 天空 168 + 雾 8×8 | ~250 |

**场景静态几何合计约 61,000 三角面**（估算，含全部实例，未做视锥剔除）。

### 2.3 视锥剔除后的单帧面数

箱庭场景玩家一次只看得到一部分。按 VR 90° 视锥 + 遮挡，**单帧可见几何估算约 40–55%**，即 **~25,000–34,000 三角面**。

| 指标 | 预算 | 估算 | 状态 |
|------|------|------|------|
| 单帧可见三角面 | <80,000 | ~25,000–34,000 | ✓ 余量充足 |
| 单帧可见顶点 | <60,000 | ~20,000 | ✓ |

结论：几何面数**不是瓶颈**。Quest 3 处理 3 万面级场景轻松。瓶颈在 DrawCall、透明排序（花瓣）、overdraw（雾/水面）。

## 三、DrawCall 预算

### 3.1 合批策略

单图集材质（`03` §3.1）是 DrawCall 控制的关键：全部不透明资产共用 `T_Palette.png`，**理论上可合批**。

| 材质 | 资产数 | 合批可能 |
|------|--------|----------|
| `M_Palette_Opaque/Stone/Wood/Metal` | 多数 | 静态合批（同图集）→ 极少 DrawCall |
| `M_Foliage_Cutout`（双面） | 樱花/竹/草 | 可合批，但双面渲染 overdraw 高 |
| `M_Petal`（BLEND 透明） | 花瓣 | **不可静态合批**（粒子，逐实例）→ DrawCall 大头 |
| `M_Water` | 水面 | 单独 1 |
| `M_Fog`（BLEND） | 雾片 | 透明，需排序 |
| `M_Lantern_Glow`/`M_Crystal_Glow`（emissive） | 灯笼/结晶 | 自发光，可合批但打断透明批次 |
| skinned（NPC/敌人） | 5+3 | **每个 skinned mesh 独立 DrawCall**，不可合批 |

### 3.2 DrawCall 预算表

| 类别 | 预算 | 说明 |
|------|------|------|
| 静态场景（合批后） | <40 | 单图集 + 静态合批 |
| skinned 角色（同时在场） | <8 | 5 NPC（分布各区，同屏 ≤2）+ 敌人（同屏 ≤3） |
| 透明（水面/雾/自发光） | <15 | 需排序 |
| 粒子（花瓣） | <20 | 每分区发射器合批为 1–2 DrawCall |
| UI（世界空间） | <10 | 名牌/对话框，仅交互时 |
| **单帧合计** | **<100** | 目标；上限 150 |

⚠️ skinned 角色是 DrawCall 硬伤——每个带骨骼动画的 mesh 无法与其他合批。控制手段：**同屏角色数上限**（见 §5）+ 远处 NPC 用 impostor/不渲染。

## 四、纹理内存预算

### 4.1 纹理清单（实测）

| 纹理 | 尺寸 | 格式 | Mip | 内存（含 mip） | 用途 |
|------|------|------|-----|----------------|------|
| `T_Palette.png` | 256×256 | RGBA8 | 是 | ~341KB | **全场景共用**，单图集 |
| `T_Petal_Alpha.png` | 64×64 | RGBA8 | 是 | ~21KB | 花瓣 alpha |

**纹理内存合计 <400KB**。这是单图集策略的巨大优势——整个场景的贴图内存不到半兆。

### 4.2 预算

| 指标 | 预算 | 实测 | 状态 |
|------|------|------|------|
| 纹理总内存 | <256MB | <0.4MB | ✓ 极充裕 |
| 单纹理尺寸 | ≤1024² | 256² | ✓ |
| 纹理数量 | 少 | 2 | ✓ |

结论：纹理**完全不是瓶颈**。反而要注意——图集太小（256²）意味着色块精度有限，若后续换精模素材（`03` §6）需重新评估纹理预算。

## 五、同屏实体预算

VR 性能的关键约束之一：**同时在场并渲染的实体数**。

| 实体类型 | 同屏上限 | 控制手段 |
|----------|----------|----------|
| NPC | 2 | 分区隔离（5 NPC 分布 5 区，玩家同屏最多 1–2） |
| 敌人 | 4 | 樱花林 3 兵 + 奥之森武者 1 + 刃 2，但分属不同交战域，同屏 ≤4 |
| skinned mesh 合计 | 6 | NPC + 敌人总同屏骨骼网格 ≤6 |
| 石灯笼（可击碎） | 全部渲染 | 静态，合批，无压力 |
| 花瓣粒子 | 见 §6 | 粒子系统 |

⚠️ 若 4 人联机 + 满敌人，同屏 skinned mesh 可能达 10+。α 单机不触发；多人联机时需引入**角色 LOD**（远处降骨骼/降面数），登记为 β 需求。

## 六、粒子预算（樱吹雪）

花瓣是**透明 + 双面 + 逐实例**，是 overdraw 和 DrawCall 的双重风险点。

### 6.1 单发射器预算

| 参数 | 值 | 说明 |
|------|-----|------|
| 单区最大存活花瓣 | 60（镜池，density 1.0） | 按 `02` §7 密度缩放 |
| 其他区 | 12–48 | density × 60 |
| 交战中 | ×0.4 | `02` §7 战斗抑制 |
| 花瓣面数 | 2 三角/片 | 单 quad |
| 单区花瓣面数峰值 | 120 三角 | 60 片 × 2 |
| 全区花瓣面数峰值 | ~400 三角 | 8 区同时（实际玩家只见 1–2 区） |

### 6.2 overdraw 控制

| 措施 | 说明 |
|------|------|
| 花瓣尺寸小 | 单片 ~0.08m，屏幕占比小 |
| 不堆积 | 落地 12s 淡出，避免地面花瓣层叠 overdraw（`02` §7） |
| 交战区降密度 | ×0.4，战斗时 overdraw 减半，且避免遮挡读招（`02` §7 玩法理由） |
| 距离剔除 | 玩家 >15m 的发射器暂停 |
| 单区发射器合批 | 同材质花瓣合批为 1 DrawCall/区 |

**预算**：单帧花瓣 overdraw <1.5× 屏幕；粒子 DrawCall <20（每区 1–2）。⚠️ 真机需用 RenderDoc/OVR Metrics 实测 overdraw。

## 七、渲染特性预算（Quest 3 移动端）

| 特性 | α 方案 | 预算/限制 |
|------|--------|-----------|
| 渲染路径 | Mobile / Compatibility（**非 Forward+**） | Quest 3 强制 |
| 光照 | 1 主定向光（烘焙）+ 1 冷调补光 + 环境光 | ≤2 实时定向光 |
| 阴影 | 主光 2048，级联 2 | ≤2 级联 |
| 实时 GI | **禁用**（烘焙 Lightmap） | — |
| SSR | **禁用**（水面用假反射/顶点动画） | — |
| 体积雾 | **禁用**（雾用交叉面片 + 顶点色，`03` asset_fog_plane） | — |
| 后期处理 | 最小化（α 无色分级，靠补光色温差，`01` §2.1） | ≤1 bloom（可选） |
| MSAA | 4×（VR 抗锯齿必需，Quest 支持） | 4× |
| 固定注视点渲染 FFR | 建议中档（Quest 支持，省边缘像素） | 中 |

## 八、内存与包体预算

| 指标 | 预算 | 估算 | 状态 |
|------|------|------|------|
| GLB 资产总体积 | — | ~1.05MB（43 个，实测） | ✓ 极小 |
| 运行时内存（几何+纹理） | <200MB | ~50MB（低模+单图集） | ✓ |
| APK 包体 | <150MB | 取决于引擎运行时（Godot ~30–50MB / UE ~100MB+） | ⚠️ 待打包实测 |
| 音频 | <20MB | 占位素材，压缩后小 | ✓ |

⚠️ APK 包体主要由**引擎运行时**决定，非本项目资产（资产仅 1MB）。Godot 导出 APK 通常 30–50MB，UE 通常 100MB+。这是 `09` 引擎选型的考量之一。

## 九、性能优化清单（按优先级）

| 优先级 | 措施 | 收益 | α 状态 |
|--------|------|------|--------|
| P0 | 单图集材质 → 静态合批 | DrawCall 大降 | ✓ 已实现（`03` §3.1） |
| P0 | 禁用 Forward+/实时 GI/SSR/体积雾 | 移动端可运行 | ✓ 方案已定（§7） |
| P0 | 花瓣不堆积 + 交战降密度 | overdraw 减半 | ✓ 已定（`02` §7） |
| P1 | 视锥剔除 + 距离剔除（发射器/远处 NPC） | 单帧实体降 | 引擎侧内置 |
| P1 | 同屏 skinned mesh ≤6 | DrawCall 控 | ✓ 分区隔离保证 |
| P1 | 烘焙 Lightmap | 免实时光照开销 | 引擎侧烘焙 |
| P2 | 固定注视点渲染 FFR 中档 | 省边缘像素 | 引擎侧开启 |
| P2 | 角色 LOD（远处降骨骼/面数） | 多人联机必需 | ⚠️ β 需求 |
| P2 | 静态几何合并（同材质 bake 成 mega-mesh） | DrawCall 再降 | ⚠️ 引擎侧可选 |

## 十、验收指标（供 `09` 引用）

| 指标 | 目标 | 测量方式 | α 可离线验证 |
|------|------|----------|--------------|
| 单帧三角面（可见） | <80,000 | 引擎 profiler | 否（估算 ✓） |
| DrawCall/帧 | <100（上限 150） | 引擎 profiler | 否 |
| 帧率 | ≥90fps（Quest 3） | OVR Metrics Tool | ⚠️ 待真机 |
| 纹理内存 | <256MB | 引擎 profiler | ✓ 实测 <0.4MB |
| 运行时内存 | <200MB | 引擎 profiler | 否 |
| APK 包体 | <150MB | 打包产物 | ⚠️ 待打包 |
| 单资产面数 | ≤`03` 预算 | validate_assets.py | ✓ 实测全通过 |
| 场景实例数 | 记录基线 159 | validate_assets.py | ✓ 实测 |

**核心结论**：本项目低模 + 单图集 + 程序化资产的策略，使几何、纹理、内存三项预算**余量极大**（实测远低于上限）。真正的风险集中在 **DrawCall（skinned 角色）** 与 **overdraw（花瓣/雾）**，二者已有明确控制手段。α 阶段最大不确定性是**真机帧率**，须待引擎与工具链就绪后实测。
